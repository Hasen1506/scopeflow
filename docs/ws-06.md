# WS-06: Messaging, capture channels & AI radar

Clients hear about change orders, invoices and reminders by email through three providers with
failover; owners share the same news on WhatsApp from their own phone (wa.me); client requests can
be captured from WhatsApp (forward-to-bot) or any app (Android share target) and checked by the
radar; AI calls survive a retired model. Inbound email stays, hardened. Nothing in this workstream
ever messages a client on WhatsApp.

## Behaviour changes

| ID | What changed |
|---|---|
| SF-19 | `lib/mail-router.ts`: every email has a class. `transactional` (review links, change orders, invoices, countersign invites) Resend → Postmark → SES; `auth` (codes, the contact-change notice to the old address) Postmark → Resend → SES; `bulk` (reminders) SES → Resend. Failover on a 5xx, a timeout (10 s) or an open circuit breaker (3 consecutive failures, 60 s); a 4xx refusal never fails over. Each provider is tried at most once per attempt, with the same idempotency key. Every email is a row in `scopeflow.mail_outbox` (`lib/mail-outbox.ts`), retried at 1, 5, 30 min, 2 h, 6 h by the notifications cron; bodies are cleared after 30 days. Bounce/complaint webhooks from all three providers feed one suppression list (`scopeflow.mail_suppressions`). |
| H18 / SF-13 | `notify(event, payload)` (`lib/notify.ts`, delivery in `lib/notify-delivery.ts`) implements all 8 Phase 0 events. Change orders and invoices are queued by database triggers on `ledger_entries` (owner change orders) and `invoices`, so the UI, the API and MCP all notify; the queue is drained by `GET /api/scopes/{id}/notifications` and the cron. The CO email carries the amount including tax ("₹472.00 (incl. GST 18%)") and the client link. Per-project `notify_client` (default on) switches off CO / invoice / reminder emails; contact-change notices, countersign invites and the account-closed notice are always sent. Each event is idempotent per (event, project, ref). The owner gets a prefilled wa.me link for the same news. |
| M18 | `POST /api/scopes/{id}/send` never changes the address on file: a different `email` answers **409 `contact_mismatch`** with `contact_change` pointing to WS-02's flow. |
| M19 | Owner text only inside fixed templates, HTML-escaped and link-free (URLs removed, bare domains defanged); the only link is the record link. "<Business> via Scopeflow" only after the owner's email is verified. Caps: 50 emails per owner per UTC day (plan-based, `SCOPEFLOW_LIMIT_MAIL_PER_DAY`), 3 per recipient per day; the 51st answers **429 `daily_cap`** with Retry-After. The first email to a recipient domain the owner never emailed answers **409 `confirm_new_domain`** until resent with `confirm_new_domain: true`. Reminders carry `List-Unsubscribe` + one-click (`/api/mail/unsubscribe`, signed per address; stops bulk mail only). Suppressed addresses answer 502 `suppressed`. |
| L7 | Inbound email matches the project by the **envelope recipient only** (`OriginalRecipient`, `envelope_to`, SES `receipt.recipients`), not To/Cc. Only the client email, cosigner emails, the owner's own sign-in address / reply-to and senders the owner released reach the radar inbox; anything else, or mail failing SPF/DKIM/DMARC, answers `{accepted: false, reason: 'quarantined'}` and is held in `scopeflow.inbound_quarantine`; `PATCH /api/scopes/{id}/inbound {quarantine_id, action: release|dismiss, allow_sender?}` releases it. |
| LT-03 / SF-01 | `lib/whatsapp-share.ts`: `waLink(phone, text)` → `https://wa.me/<E.164 digits>?text=…` (or `https://wa.me/?text=…`), polite messages for scope / change order / invoice / reminder in en, hi, ta. Slot `app/components/slots/whatsapp-share.tsx` (`WhatsAppShare`, `ClientNotice`), editable before sharing. `/share?project=<id>` is WS-06's own "tell the client" view. |
| SF-10 | `sendOtpMessage(channel, to, code, {fallbacks})` in `lib/sms.ts` for WS-02: WhatsApp through the Meta Cloud API `authentication` template (code in the body and the copy-code button), Twilio/MSG91 kept; email through the `auth` class; on failure the caller's fallbacks are tried in order. The destination is always the one the caller passed. |
| SF-04 | `POST /api/whatsapp/webhook`: X-Hub-Signature-256 checked (401 otherwise); the owner links a phone in Account → WhatsApp with a WhatsApp code and consent. A forwarded text from a linked phone is matched to a project (named, the only one, the only recently active one, or an interactive "Which project?" list), checked by the radar, and answered (service-window reply, to that owner only) with the verdict, the clause and a `/share?capture=…` link to the prefilled change order. Unlinked numbers get an onboarding reply and nothing is stored; a number on file as a client gets no reply. Voice notes: "not transcribed yet". `UNLINK` disconnects. |
| SF-03 | `public/manifest.webmanifest` `share_target` (POST multipart text/url/files → `/api/share`) → `/share`: sign in, pick the project, radar verdict with the cited clause, change order prefilled with a price from the rate card (WS-05's `scopeflow.rate_cards`, when present) or the owner's price history, propose, then "Back to WhatsApp". `public/sw-share.js` caches nothing. Shared images are counted, not read. |
| M11 | `/api/draft` currency: request > owner default > mode default; an explicit request is final even if the brief names another currency. Response adds `currency_source`. |
| L11 | Model registry with ordered fallbacks per tier (`SCOPEFLOW_MODELS`, else the env models plus built-in fallbacks). A model answering 404 / "deprecated" is replaced by the next and a readiness warning is written to `scopeflow.readiness_warnings` (read by WS-10's `/api/readiness`). `scripts/check-models.mjs` checks the whole chain and records/clears warnings. |
| Reminders | `scripts/send-reminders.mjs` sends through the `bulk` class with the outbox, suppression, caps and List-Unsubscribe. An invoice paid net of TDS (open ≤ uncredited TDS, from the invoice snapshot's `tds` and, when present, `scopeflow.tds_credits`) is never chased; instead a TDS-certificate (Form 16A) reminder goes out at most once per quarter after the certificate for the quarter of deduction is due, four at most. Payment reminders ask only for the cash part. Projects tombstoned by WS-08 (`projects.owner_deleted`) and projects with `notify_client` off get no reminders. |

## Operator steps

1. Verify the `SCOPEFLOW_MAIL_FROM` domain at Resend, Postmark and SES (SPF include + DKIM for each); set the three credentials. Postmark: a transactional stream for `auth`.
2. Point bounce/complaint webhooks at `/api/mail/events/resend` (Svix secret → `RESEND_WEBHOOK_SECRET`), `/api/mail/events/postmark` (Basic auth, password `SCOPEFLOW_MAIL_WEBHOOK_SECRET`), and an SNS topic for SES bounces/complaints → `https://<app>/api/mail/events/ses?token=<SCOPEFLOW_MAIL_WEBHOOK_SECRET>` (the subscription is confirmed automatically).
3. New Render crons (WS-10 owns the schedule): `node scripts/drain-notifications.mjs` every 5 minutes; `node scripts/check-models.mjs` daily (own cron); the existing daily `scripts/send-reminders.mjs`.
4. WhatsApp (needs an approved WABA): create the `authentication` template, set the WhatsApp variables, subscribe the app's webhook to `messages` at `/api/whatsapp/webhook`. Without them the bot and WhatsApp codes are off; wa.me share links always work.
5. Inbound email unchanged: Postmark Inbound or SES receiving → `/api/inbound/email`; the payload must carry the envelope recipient (Postmark `OriginalRecipient`).
