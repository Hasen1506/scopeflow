# WS-02: Evidence, signing & client identity

Every evidence claim ScopeFlow makes is now true. Signing fails closed in production, receipts say
exactly what they prove (plan §6.1, §6.2), each countersigner has their own identity, drafts never
leak to a client, decided records survive revoke and rotate, one-time codes are single-use and
rate- and cost-limited, and the verify flow works from what the client can actually see.

## Behaviour changes

| Item | Before | Now |
| --- | --- | --- |
| C1 | Production could record unsigned decisions (`signing: off`). | In production, unless `signingStatus()` is `dedicated`, the decision, countersignature and contact-change routes answer **503 `signing_unavailable`** ("This record can't be signed right now; nothing was saved") and write nothing. Receipts carry `Signed (Ed25519)` + key id and the §6.1 seal line; unsigned legacy records read "Recorded by ScopeFlow; not sealed (sealing was not configured when this was saved)". |
| C6 | The cookie-secret-derived key verified records in production. | `verificationKeys()` trusts it only outside production, with `SCOPEFLOW_ALLOW_COOKIE_SIGNING=1`, or when its key id is in `SCOPEFLOW_LEGACY_KEY_IDS`; `/api/verify` then answers `signature: "legacy_key"` (chip "Verified · older seal"), otherwise `unknown_key`. Retired dedicated secrets (`SCOPEFLOW_SIGNING_SECRET_PREVIOUS`) stay fully trusted. `/api/signing-key` lists every trusted key (current first; others with `status`). |
| C5 | Receipts implied identity; the client contact could be repointed silently. | Owner-session approvals are allowed and flagged on the client page (`evidence.owner_session`), in the workspace (`project.owner_session_versions`) and on the PDF. `evidence.statement`: "Approved by whoever held this link…", with a code: "…after entering a code sent to s***@e***.com, the address on file for this client since 3 Oct 2026." The contact locks once any version is sent (email send, copied/shared link, decision): `PATCH` → **409 `contact_locked`**. The only change path is `POST /api/scopes/:id/contact-change {email\|phone, reason, confirm: true}` (fresh browser session): notice to the OLD address (`notify('contact_changed_old_address')`), signed `contact_history` record shown in the client timeline, new "on file since" date. |
| H1 | Anyone with the client link could countersign as any role. | Roles carry their own `{name, email\|phone}`; each gets `/cosign/<token>` and a code to that role's own address. The client link's `POST /cosign` answers **403 `use_your_cosigner_link`**. Records show the masked verified address. |
| M17 | Roles editable after approval. | Frozen into the version at first send; `PATCH cosigners` afterwards → **409 `roles_frozen`**. |
| H2/M29 | `previous` was version−1, even an unsent draft. | The diff base is the last version this client approved, else the last one sent/opened; never a draft, never revoked. `compare_versions` + `?compare=N` offer only those. |
| H4 | Revoking/rotating a decided version killed the client's record. | Decided + revoke: link stays **200 read-only** (`readonly: true, readonly_reason: 'revoked'`): record, ledger, invoices, receipt, statement; no decision, code, payment or cosign. Decided + rotate: new token; the old one is a read-only alias (`readonly_reason: 'rotated'`). Pending + revoke is still 404. |
| H5 | Rotating any link restarted the latest version's expiry. | Expiry is per version (`version_links.link_issued`). |
| M14 | One code session could back several records. | Sessions are bound to `{version, action, target}` and consumed on use; a second use answers **401 `otp_required`** (via `checkDecisionProof`). |
| M15 | No send limits beyond 3 per 10 minutes. | Per version 5 codes / 24 h, per destination 10 / 24 h, cooldown 0 → 30 s → 2 min → 10 min, per-owner daily budget (`SCOPEFLOW_OTP_DAILY_BUDGET`, units: email/WhatsApp 1, SMS 5). **429** with `retry_after` + `Retry-After`. Spend metered in `otp_spend` (`otpSpendToday()`, `otpSpendTotals()`). |
| M16 | API tokens could switch off identity checks. | `client_email`, `client_phone`, `require_otp`, `otp_channel`, `cosigners` and contact-change need a browser session signed in within 10 minutes: tokens/OAuth → **403 `session_required`**, stale session → **403 `reauth_required`**. |
| L1 | — | `content_sha256` = SHA-256 of `canonical(content)` (lib/evidence.ts, same in the browser); mismatch → **409 `content_changed`**. Canonical form unchanged. |
| L2 | "signature" overclaims. | "Electronic acceptance (typed name + click), recorded and sealed by ScopeFlow"; "digital signature" only for PAdES / Aadhaar eSign. |
| L3 | Expiry shown in UTC. | `link_expires_text` / 410 message in the project zone: "13 Oct 2026, 1:30 am IST". |
| L12 | 409 with no pointer. | **409 `replaced`** with `newer_version` and `newer_url` (when that version was handed out); GET on a stale link also carries them. |
| LT-09 | /verify needed the 64-char fingerprint the page never showed. | The evidence block shows the full fingerprint, a copy button and "Verify this record" (`/verify?p=&v=&a=`); `/api/verify` also accepts the 16-char prefix. |
| QA-02 | Footer routed "not-a-receipt" to /verify. | `parseReceiptInput()` + inline "That doesn’t look like a ScopeFlow receipt"; /verify has an inline "Paste a receipt" box; `ReceiptCheckForm` is ready for the footer (WS-09 mount). |
| QA-03 | "Fingerprints match · not signed". | Chips per §6.1 (`chipWording()`). |
| QA-01 (receipt half) | Receipt rendered (and PAdES-signed) on every download. | Cached by a hash of everything in it (`receipt_cache`); header `X-Receipt-Cache: hit\|miss`. |
| SF-15 | — | `lib/esign/*` provider interface, Leegality adapter, local double. Per-version opt-in `POST /api/scopes/:id/esign {version}`; callback `POST /api/esign/<provider>/callback` stores the signed PDF (SHA-256) and audit trail; receipt and chip then say "Aadhaar eSign". |

## Migration `0017_ws-02_trust_identity.sql`

Additive and idempotent: `version_links` (per-version `link_issued`, `first_sent`, frozen `cosigners`; a side table so every `SELECT v.*` and its goldens stay identical), `cosign_invites`, `version_link_aliases`, `review_otps.action/target/consumed`, `otp_spend`, `contact_history` (immutable), `esign_records`, `receipt_cache`, `projects.contact_since`; `projects.owner_deleted`/`retain_until` and `idempotency_keys` repeat WS-08's / WS-10's definitions with `IF NOT EXISTS`. Backfills: project `link_issued` → latest version; `first_sent` for decided and emailed versions; frozen roles for sent versions; `contact_since` = project creation. A trigger on `projects.last_sent` marks emailed versions sent.

## Environment

| Variable | Where | Notes |
| --- | --- | --- |
| `SCOPEFLOW_SIGNING_SECRET` | **required in production** | ≥ 32 random characters, stable. Set on Render **before** deploying this branch, or decisions return 503 by design. Rotate by moving the old value to `SCOPEFLOW_SIGNING_SECRET_PREVIOUS`. |
| `SCOPEFLOW_SIGNING_SECRET_PREVIOUS` | optional | Comma-separated retired secrets (still verify). |
| `SCOPEFLOW_LEGACY_KEY_IDS` | optional | Key ids of records sealed with the cookie-derived key before the dedicated secret existed. Find the id with `cookieKeyId()` (lib/signing.ts) or from a stored signature's prefix. |
| `SCOPEFLOW_ALLOW_COOKIE_SIGNING` | keep **unset** | Only for a migration window; never fixes C1 (production signing still needs the dedicated key). |
| `SCOPEFLOW_OTP_DAILY_BUDGET` | optional | Per-owner daily code budget in units (default 200). |
| `SCOPEFLOW_ESIGN_PROVIDER` | optional | `leegality` (needs `LEEGALITY_AUTH_TOKEN`, `LEEGALITY_PRIVATE_SALT`, optional `LEEGALITY_BASE_URL`, `LEEGALITY_PROFILE_ID`) or `double` (local only, with `SCOPEFLOW_ESIGN_DOUBLE_SECRET`, refused unless `APP_URL` is localhost). |

## Operator steps

1. Set `SCOPEFLOW_SIGNING_SECRET` on Render, then deploy (preDeploy runs the migration).
2. Confirm `/api/signing-key` shows `signing: "dedicated"` and one key, and `/api/health` is 200 (WS-10).
3. If old records were sealed with the cookie-derived key, add its key id to `SCOPEFLOW_LEGACY_KEY_IDS`.
4. Leegality: needs an account; the adapter's field names follow the v3.1 sign-request API and must be confirmed against the account's docs before enabling.
