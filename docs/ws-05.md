# WS-05: Scope ledger, change orders, retainers and rate card

Branch `hark/ws-05-ledger-retainers`, based on `hark/ws-00-contracts` (Phase 0). Migration slot `0018`.
Covers H6, H17, M8, LT-08, LT-14, SF-05, SF-06 (primary), M5 for change orders (wired for WS-01), and
supports C4 / H14 (WS-04), M7 (WS-03) and SF-26 (WS-10).

## Behaviour changes

### Money is never dropped (H6)
- `lib/ledger-hooks.ts` `appendMoneyEntry()` writes `payment`, `payment_received`, `refund`,
  `tds_credit`, `excess_payment`, `payment_claim_confirmed` and `baseline_superseded` entries.
  - Exempt from the plan entry cap. The cap (`limits().ledger_entries`, 200 on beta) now counts only
    against **owner-authored, non-money** kinds (`countsTowardCap` in `lib/ledger.ts`). System and client
    entries and every money kind always land; this also applies to the existing webhook path.
  - Recorded against the **current approved** baseline, even while a newer version is pending; when the
    order was created on an older baseline the payload keeps `order_baseline`.
  - Idempotent by `ref` (returns the existing entry with `duplicate: true`), retries when the ledger moves,
    and throws `MoneyEntryError` (`not_money_kind | invalid_payload | no_approved_baseline | conflict`)
    instead of failing silently. WS-04 turns that into a 500 + `payment_alerts` row + owner mail.
- `onBaselineApproved(project, from, to)` writes one signed `baseline_superseded` entry carrying the money on
  the record (received, refunded, paid, TDS, invoiced, entry count) when an approval supersedes an approved
  version (C4, plan §6.4). Idempotent by ref `superseded:<from>:<to>`. WS-02 calls it from the decision route.

### Change-order content proof (H17)
- `coCanonical()` / `coSha256()` (`lib/ledger.ts`): SHA-256 of `scopeflow-co-v1|` + the canonical CO as
  rendered: seq, title, added deliverables (id, title, qty, unit, acceptance), removed ids, currency,
  `fee_delta_minor`, tax (label, pct, amount), `total_incl_tax_minor`, days, rounds, bank. Status is not part
  of it.
- `POST /api/review/[token]/change-order` accepts `acknowledged: true` and `co_sha256`. The server recomputes
  the hash from the ledger: missing/invalid proof → **400 `co_proof_required`**, mismatch → **409
  `co_changed`**. With proof, the settle entry payload stores `acknowledged`, `co_sha256` and
  `total_incl_tax_minor` (the tax-inclusive amount the client saw). The receipt returns `co_sha256`,
  `total_incl_tax_minor` and `proof_recorded`.
- **Compat path (default):** until WS-07 mounts `CoCard` on the client page, a decision in the pre-WS-05
  shape (neither field) is still accepted and recorded exactly as before (no proof fields in the payload, so
  existing exports and the e2e `export.json` golden are unchanged); its receipt still reports the hash the
  server computed. **`SCOPEFLOW_CO_PROOF=strict`** refuses that shape with 400 `co_proof_required`.

### Change-order money (M5, for WS-01)
- `checkEntry('change_order')` rejects a `fee_delta`, or an added deliverable `price` / `unit_price`, with more
  decimals than the agreement currency allows (INR/USD 2, JPY 0): 400 `Fee change: Use at most 2 decimals`.
  `changeOrderMoneyProblems()` in `lib/ledger.ts` mirrors WS-01's function of the same name in
  `lib/scope.ts`; once WS-01 lands, it should delegate to it (see the PR's change requests).

### Bounded dates (M8)
- `client_input.received`, `revision_round.feedback_date`, `tds_credit.credited`,
  `payment_claim_confirmed.received`, `delivery_accepted.accepted` and retainer `usage.date` must be
  ≤ today in the project's time zone + 1 day and ≥ the baseline approval date (same zone). Otherwise 400 and
  nothing (due date, delays) changes. `entryContext()` in `lib/ledger-math.ts` supplies the dates.

### Revise and withdraw (LT-08)
- `POST /api/scopes/[id]/ledger` with `kind: change_order` and `payload.revises: n` withdraws CO-n and
  proposes the replacement in **one transaction** (`appendEntries`): both entries land or neither does.
  Only a CO awaiting the client can be revised (409 `not_revisable`).
- Withdraw (`settle` with `outcome: withdrawn`) is idempotent (a repeat answers 200 `replayed`) and skips the
  project advisory lock; the conditional INSERT and the unique `(project, seq)` / `settle:<n>` ref keep it
  correct under a double click. The workspace updates optimistically and ignores a second click.

### Deliverables fold (LT-14)
- `computeAgreement()` adds `agreement.deliverables`: the deliverables now in force (baseline plus approved
  COs), one line each, CO items suffixed `[CO-n]`. The CO form nudges "Add the deliverable this pays for" when
  a fee change has no deliverable (warning, never a block).
- Golden note: `tests/golden/ledger.golden.json` gained this derived `agreement.deliverables` field. It is a
  fold output (WS-05 owns ledger fold goldens); no hash, signature or receipt input changed.

### Retainers (SF-05)
- Scope `engagement: 'retainer'` + `retainer: {period: 'monthly', quotas: [{item_id, qty}], carry_over:
  'none' | 'cap', renewal?: 'auto' | 'manual'}`. The scope fee is the fee for one period.
- Ledger kinds `period_open` (quotas granted, with carried balance), `usage` (+n of an item) and
  `period_close` (the period's statement lines). `lib/retainer.ts` folds them (`retainerState`,
  `retainerStatement`).
- `GET /api/scopes/[id]/periods` returns the live counters; `?period=YYYY-MM` adds the monthly statement data
  (fee, overage COs, tax, total) for WS-03's statement/invoice. `POST` with `action: usage | open | close`.
  The first usage of a month opens it. Usage past a quota proposes **exactly one** overage change order per
  usage entry, in the same transaction, priced from the rate card (else the scope unit price, else unpriced).
  Owners cannot hand-write an `overage` CO.

### Rate card (SF-06)
- `scopeflow.rate_cards`: one per account. Items `{id, title, unit, unit_price_minor, currency, tax_pct,
  tags}`, multipliers `{id, label, pct}` (default rush +25 %). `GET/PUT /api/rate-card`;
  `POST /api/rate-card/quote` prices an item (multipliers then tax, half-up in minor units at each step;
  with `project_id` the agreement's tax applies) and returns a CO draft carrying `rate_card` provenance.
- `rateCardFor(owner)` (`lib/rate-card.ts`) is the read API for WS-06's radar.

### Entry kinds enabled
`baseline_superseded`, `tds_credit`, `excess_payment`, `delivery_accepted`, `payment_claim_confirmed`,
`period_open`, `usage`, `period_close` now have payload schemas. Existing kinds keep their exact payloads and
hash-chain format (differential test against the pre-PR fixture).

### MCP (SF-26)
`lib/mcp-ledger.ts` exports `ws05LedgerTools`, `ws05LedgerValidators`, `ws05WriteTools` and
`runWs05LedgerTool`: `list_rate_card`, `quote_rate_card_item`, `get_retainer`, `propose_retainer_usage`,
`revise_change_order`. WS-10 registers them.

### Slots
`app/components/slots/co-card.tsx`, `retainer-counter.tsx`, `rate-card-picker.tsx` are implemented; plus
`app/retainer-panel.tsx` and `app/rate-card-settings.tsx`. The workspace ledger panel already shows the
retainer panel (retainer projects) and the rate-card picker in the CO form.

## Migration
`db/migrations/0018_ws-05_ledger_retainers.sql` (additive, idempotent): `scopeflow.rate_cards`, a partial index
for retainer kinds, and the `ledger_entries_kind_check` constraint listing every kind the app writes. A
later workstream adding a kind replaces the constraint in its own migration.
